# Epic 1 Context: 安静可靠的后台记录

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 1 建立专注记录器可信的本地记录底座：一个 Windows WPF 单进程桌面应用能够安静驻留后台，通过托盘暴露被动状态，按应用级别采样前台活动，把 focus、idle、paused、locked、sleeping 等片段可靠写入本地 SQLite，并在空闲、锁屏、睡眠、暂停、恢复和本地跨日时切清边界。它的价值不是完成最终报表，而是让后续报表、分类和数据控制都有一份隐私边界明确、可恢复、可解释的本地事实源。可用 planning artifacts 包含 epics、PRD/addendum、architecture 和 UX/design；未发现 product brief，因此本文不引入产品简报独有约束。

## Stories

- Story 1.1: 启动后保持后台宿主与托盘状态
- Story 1.2: 用本地 SQLite 保存最小专注片段
- Story 1.3: 按应用名采样前台应用且不采集内容
- Story 1.4: 处理空闲、锁屏、睡眠、暂停和跨日边界

## Requirements & Constraints

- 应用必须能后台运行并支持开机自启动开关；关闭主窗口只隐藏界面，不停止后台宿主。只有用户显式退出才有序停止宿主和记录协调器，并关闭开放片段。
- 正常记录必须完全无打扰：不弹出专注提醒、效率评分、每日评价、确认问题或监督式通知。采集、权限或启动异常只能在主界面或托盘状态中被动展示，并写入本地日志。
- 采样粒度只能到应用身份。允许持久化采样时刻、应用显示名、可执行文件名或 Windows 包标识、稳定应用身份；不得保存窗口标题、网页标题、文档名、文件路径、聊天对象、截图、键盘输入、鼠标轨迹、窗口内容或长期进程 ID。
- 默认采样间隔为 5 秒；少于 15 秒且前后稳定应用身份相同的短暂切换应合并，避免统计噪声。
- 空闲阈值默认 5 分钟，后续由本地设置控制在 1-60 分钟。空闲、暂停、锁屏、睡眠和排除时段都不能计入专注总时长；恢复输入或恢复记录后，从当前活跃应用开始新 focus 片段。
- v1 必须本地优先且离线可用；Epic 1 的记录事实、设置和日志写入当前用户本地 SQLite，不引入账号、后端、遥测或上传路径。
- 正常运行一天后，连续前台活动漏记不应超过约 1 分钟。后台记录平均 CPU 目标低于 1%，内存低于 150 MB。
- 测试不得调用真实 Win32 API，也不得包含真实用户活动数据；协调器、时间边界和仓储行为使用合成采样、会话、电源和时钟信号验证。

## Technical Decisions

- 架构采用分层单进程 WPF：App shell 承载主窗口、托盘和组合根；Application services 承载命令、查询、端口和 `RecordingCoordinator`；Domain 定义片段与记录规则；Infrastructure 封装 Win32、SQLite、开机启动和本地日志。
- `RecordingCoordinator` 是唯一能创建、关闭、拆分、合并和 checkpoint 片段的组件。UI 和托盘提交命令；Win32 活动适配器与会话/电源适配器只发布信号；协调器按单序列处理采样、空闲、锁屏、睡眠、暂停、恢复和跨日边界。
- SQLite 是唯一持久化事实源。Epic 1 只创建记录所需 schema：迁移、focus segment、application identity、记录相关 settings 和本地结构化日志；分类、排除和导出 schema 留给后续需要它们的故事。
- 片段 `disposition` 使用稳定字符串：`focus`、`idle`、`excluded`、`paused`、`locked`、`sleeping`。`ApplicationIdentityId` 仅对 `focus` 必填；非专注片段不保存应用身份。
- 稳定应用身份由应用显示名与可执行文件名或 Windows 包标识组成。优先使用包标识；否则对显示名做 Unicode 规范化、对可执行文件名小写化。完整路径和进程 ID 只能在单次 Win32 查询中短暂使用，归一化后丢弃。
- 所有片段边界以 UTC 即时点保存，同时在创建或拆分时写入当时的 `local_date` 和 UTC 偏移。跨本地午夜的片段由协调器拆分；历史报表、导出和单日删除后续按存储的 `local_date` 分组。
- 开放片段创建时落盘，并约每 30 秒在 SQLite 事务中更新 checkpoint 结束时间。启动恢复时，仓储把遗留开放片段关闭到最后 checkpoint，随后协调器只在收到新的合格信号后开始新片段。
- 会话和电源边界由隐藏消息窗口适配器提供：注册当前会话通知，处理锁屏/解锁和系统挂起/恢复事件，并把边界信号交给协调器。
- 约定：C# 类型使用 PascalCase；命令以 `Command` 结尾，查询以 `Query` 结尾，端口接口以 `I` 开头；SQLite 主键为 UUID 文本，枚举以稳定字符串保存，持久化时间使用 UTC ISO 8601。

## UX & Interaction Patterns

- 托盘是被动控制入口：左键打开或聚焦主窗口，右键提供菜单。菜单至少要支撑打开报表、暂停/恢复、查看状态和退出这些生命周期操作的路径。
- 主窗口初始化和关闭行为要验证后台宿主仍运行；关闭窗口不得退出记录，显式退出才停止。正常记录状态不弹通知。
- 暂停状态必须在托盘或主界面可见；恢复后从当前活跃应用开始新片段。`Esc` 或关闭窗口不应成为退出记录的快捷路径。
- 错误和权限问题以中性短文案显示在托盘/设置/主界面状态中，例如说明当前无法采集并会继续重试；不得追问用户刚才做了什么。
- 视觉和文案保持 Windows 工具感：Segoe UI、紧凑信息布局、最多 8px 圆角、被动状态文本；避免“浪费”“高效”“低效”“失败”、评分、成就或监督语气。
- UI 不展示窗口标题、文件路径、网页标题、聊天对象、截图、键盘输入或鼠标轨迹；应用身份展示只能使用安全摘要。

## Cross-Story Dependencies

- Story 1.1 先建立单进程生命周期、托盘入口和命令路由；后续记录、暂停/恢复和显式退出都依赖这个宿主边界。
- Story 1.2 可以先用合成信号完成 SQLite schema、片段写入、checkpoint 和启动恢复；它为真实采样与状态切换提供事实模型。
- Story 1.3 将 Win32 前台应用采样接入既有协调器边界，必须保持 Story 1.2 已建立的隐私字段限制和稳定身份规则。
- Story 1.4 在 Story 1.2 的片段模型上扩展空闲、锁屏、睡眠、暂停、恢复和本地跨日状态转换，并验证非专注时段不污染 focus 统计。
- Epic 2 的报表和分类依赖 Epic 1 产生的 `focus` 片段、应用身份和本地日期归属；Epic 3 的设置、排除、删除和导出会复用同一 SQLite 事实源与协调器命令边界。
