# Epic 1 Context: 安静可靠的后台记录

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

建立专注记录器可信的本地记录底座：一个 Windows WPF 单进程应用安静驻留后台，通过托盘提供被动状态，在主窗口关闭后仍持续记录应用级活动，并可靠保存可解释的本地片段。它必须正确切分空闲、锁屏、睡眠、暂停、恢复与跨日边界，同时严格保护隐私；后续报表、分类和数据控制都依赖这一事实源。

## Stories

- Story 1.1: 启动后保持后台宿主与托盘状态
- Story 1.2: 用本地 SQLite 保存最小专注片段
- Story 1.3: 按应用名采样前台应用且不采集内容
- Story 1.4: 处理空闲、锁屏、睡眠、暂停和跨日边界

## Requirements & Constraints

- 应用支持后台运行；关闭主窗口仅隐藏 UI，显式“退出”才有序停止后台宿主和记录协调器，并不留下新的开放片段。每个 Windows 用户会话只允许一个实例；第二实例请求现有实例显示或激活主窗口后退出。
- 托盘提供打开报表、暂停/恢复、状态查看和退出。正常记录不弹系统通知、模态窗口、提醒、评分、确认问题或监督式文案；启动、权限和采集异常只能通过本地日志及主界面或托盘的被动状态呈现。
- 只采集应用级信息：采样时刻、显示名、可执行文件名或 Windows 包标识，以及当前会话空闲时长。不得采集或持久化窗口/网页/文档标题、完整路径、聊天对象、截图、键盘输入、鼠标轨迹、窗口内容或长期进程 ID。
- 默认每 5 秒采样；若短暂切换少于 15 秒且前后稳定应用身份相同，合并回同一片段。空闲阈值默认 5 分钟（后续设置可调整为 1–60 分钟）。
- 空闲、暂停、锁屏、睡眠和排除时段不计入专注。恢复输入或恢复记录时，从当前活跃应用建立新的 focus 片段；跨本地自然日必须切分。
- v1 离线、本地优先，无账号、后端、遥测、HTTP 客户端或上传路径。后台平均 CPU 目标低于 1%，内存低于 150 MB；连续前台活动的可恢复漏记上限约 1 分钟。
- 领域与应用测试使用合成采样、会话、电源和时钟信号，不调用真实 Win32 API，也不使用真实用户活动数据。

## Technical Decisions

- 分层单进程 WPF：App shell 承载主窗口、托盘和组合根；Application services 提供命令、查询、端口与 `RecordingCoordinator`；Domain 定义片段规则；Infrastructure 封装 Win32、SQLite、开机启动和本地日志。
- 只有 `RecordingCoordinator` 能创建、关闭、拆分、合并或检查点持久化片段。UI/托盘仅提交命令，采集与会话/电源适配器仅发布信号；协调器按单一序列处理信号，归一化或忽略乱序和同刻重复信号，并写入无敏感信息日志。
- SQLite 是唯一事实源。Epic 1 建立迁移、片段、应用身份、记录相关设置和本地结构化日志；分类、排除和导出表留给后续故事。所有用户写入在单一 SQLite 事务中完成。
- 片段状态以稳定字符串保存：`focus`、`idle`、`excluded`、`paused`、`locked`、`sleeping`；只有 `focus` 计入专注。`ApplicationIdentityId` 对 `focus` 必填，其他状态为空。
- 稳定身份由显示名与可执行文件名或 Windows 包标识组成，优先包标识；否则规范化显示名与小写可执行文件名。完整路径和进程 ID 仅用于一次 Win32 查询后即丢弃；无法获得身份时不创建 focus 片段。
- 所有边界保存为 UTC，并在创建/拆分时持久化当时的 `local_date` 和 UTC 偏移。开放片段创建即落盘、每 30 秒更新检查点；启动时将遗留开放片段关闭到最后检查点，之后等待新的合格信号。
- 隐藏消息窗口是会话和电源边界的唯一来源：注册当前会话通知，转发锁定/解锁及挂起/恢复信号；注册失败仅更新被动本地状态。
- C# 类型用 PascalCase，命令以 `Command` 结尾、查询以 `Query` 结尾、端口接口以 `I` 开头；SQLite 主键为 UUID 文本，时间为 UTC ISO 8601，枚举使用稳定字符串。

## UX & Interaction Patterns

- 托盘是被动控制入口。打开报表应显示或聚焦主窗口且不改变记录状态；关闭窗口或 `Esc` 不能变成退出记录的快捷路径。
- 托盘和主界面应清晰呈现正在记录、已暂停及故障等状态。暂停/恢复后的状态改变立即可见；错误采用中性、简短、可解释的文案，不追问用户活动内容。
- 保持 Windows 工具型、低装饰界面和中性语气；不得使用“浪费”“高效”“低效”“失败”等评价或监督语言。界面只显示安全的应用身份摘要，不显示任何内容级数据。

## Cross-Story Dependencies

- Story 1.1 建立单实例生命周期、后台宿主、托盘与退出命令边界；其余故事接入该宿主而不自行管理进程生命周期。
- Story 1.2 先提供 SQLite schema、片段写入、检查点和恢复模型；Story 1.3 的真实采样与 Story 1.4 的状态边界均使用该模型和协调器。
- Story 1.3 必须保持 Story 1.2 的稳定身份与最小采集边界；Story 1.4 扩展其片段状态转换，并保证非 focus 状态不污染统计。
- Epic 2 依赖 focus 片段、应用身份和固定的本地日期归属；Epic 3 复用同一 SQLite 事实源与协调器命令边界来实现设置、排除、删除和导出。
