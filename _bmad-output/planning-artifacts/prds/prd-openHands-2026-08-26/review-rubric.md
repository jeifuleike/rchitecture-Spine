# PRD Quality Review — 专注记录器

## Overall verdict

总体 verdict：Good。以个人自用、低风险、Windows 桌面小工具的校准来看，这份 PRD 已经有清楚的产品原则：粗粒度、稳定、无打扰、本地优先；功能也基本能支撑后续 UX、架构和故事拆分。主要风险不在方向，而在若干验收边界还偏软，尤其是采样/片段规则、应用身份、报表完成标准、导出范围和本地数据保留默认值。

## Decision-readiness — adequate

PRD 可以支持进入轻量实现规划。§1 明确写出核心判断：“粗粒度但稳定、无打扰的记录比细粒度但侵入的分析更重要”，§6 又把网页级、文件级、评分、提醒、团队管理和云账号排除出 v1，这些都让决策者知道产品要拒绝什么。

它没有把矛盾粉饰掉：§9 将工作名、空闲阈值、报表形态、数据保留、AI 对话分类和未来同步字段列为开放问题。对于当前 stakes，这些开放问题不是致命缺陷；但在开工前，至少数据保留、采样/空闲细节和导出范围需要被转成默认决策或明确延期，否则实现者会各自补答案。

- 无需要单列的 finding；相关缺口在 Done-ness clarity 和 Scope honesty 下列出。

## Substance over theater — strong

内容基本是 earned content，而不是模板家具。目标用户只有 Stove 一个实际操作者，UJ 也只有两个负重旅程；非目标用户和非目标范围都直接服务于隐私与无打扰原则，没有为了显得完整而扩写企业、增长或平台叙事。

NFR 也不是泛泛的“安全、可靠、可扩展”：§5 明确了 v1 不上传、不采集截图/键盘/网页标题等隐私边界，并给出 CPU 与内存预算。作为个人桌面工具，这个详细度是合适的。

### Findings

- **low** 价值判断式分类名会轻微削弱“无监督”原则（§3 术语表 / FR-5） — 默认分类包含“无效/摸鱼”，但 §1 写明“不监督、不提醒、不打断”，SM-C1 也说“不替用户判断价值”。这个词很贴近个人口语，但如果成为默认 UI/数据分类，会让产品语气滑向评判。*Fix:* 将默认分类改成更中性的“休闲/其他”或“用户自定义负向分类”，把“无效/摸鱼”保留为用户可改名示例。

## Strategic coherence — strong

PRD 有统一 thesis：后台自动记录应用级活动，事后提供可解释的本地统计，同时避免内容级采集和监督感。FR-1 到 FR-12 都服务于这条线，没有出现番茄钟、目标管理、网站拦截、AI 教练之类会把产品推向另一类工具的功能。

成功指标也基本验证这条 thesis：SM-1 关注“连续 7 天无手动干预仍可查看统计”，SM-3 关注分类够用，SM-C1/SM-C2 明确不优化娱乐减少、提醒次数或打开频率。它们不是单纯活动量指标。

## Done-ness clarity — adequate

每个 FR 都有“可测试结果”，这对后续拆 story 很有帮助。FR-2 明确只记录应用名粒度，FR-4 明确不得弹提醒/评分，FR-8/FR-9 明确本地优先和未来同步边界，整体比常见轻量 PRD 更可验收。

不足在于几个核心行为还没有落到足够具体的完成标准。对这个产品来说，记录是否可信取决于采样频率、片段切分、空闲恢复、应用身份和报表计算口径；这些如果不写清，工程实现会补上隐性规则。

### Findings

- **medium** 采样精度与专注片段生成规则还不可验收（§4.1 / FR-2 / FR-3 / §5） — PRD 使用“定期识别”“按固定频率”“明显漏记”等表述，但没有定义采样间隔、应用切换多快算一次切换、短暂切换是否合并、锁屏/睡眠/跨日如何切片。*Fix:* 为 v1 增加轻量默认：采样间隔、片段最小持续时间/合并规则、空闲开始与恢复后的切片规则，以及“连续运行一天”的可接受漏记口径。
- **medium** 应用身份字段把实现引向不稳定分类（FR-2 / 假设索引 / addendum 实现提示） — FR-2 写“应用进程标识”，假设索引写“保存进程标识用于稳定分类”，addendum 又举例 `process_id`；但 Windows 的进程 ID 每次启动都可能变化，不能作为稳定分类键。*Fix:* 在 PRD 术语表或 FR-2 中把“稳定应用身份”定义为应用显示名 + 可执行名/包标识等非内容级字段，并明确不保存文件路径或窗口内容。
- **medium** 报表完成标准仍偏内容清单，缺少计算口径（FR-6 / FR-7 / SM-2） — FR-6 要展示自然日应用/分类累计、Top 应用和 Top 分类，FR-7 要“列表和基础占比”，但没有说明自然日按本机时区、Top 的排序与并列处理、时长四舍五入、空闲时间是否进分母、未分类项如何影响总计。*Fix:* 给报表增加 4–6 条口径级验收条件，保持轻量即可。
- **medium** 删除与导出的范围不一致（FR-12 / §7.1） — FR-12 正文写“导出本地统计或原始记录”，可测试结果只写“导出本地统计摘要”，§7.1 也只列“导出本地统计摘要”。这会影响数据模型、隐私提示和导出 UI。*Fix:* 选择一个 v1 范围：若只导出统计摘要，删除“原始记录”；若允许原始记录导出，补充字段、格式和用户确认。

## Scope honesty — adequate

PRD 的非目标做得很好：§2.2、§6、§7.2 反复排除了团队监控、内容级分析、AI 总结、云同步和监督机制，读者不需要猜 v1 会不会偷偷扩张。假设索引也把主要推断集中起来，适合低风险个人项目。

它的 scope honesty 还差一步：部分开放问题虽被诚实列出，但已经会影响 MVP 的存储与验收边界。尤其是本地数据默认保留多久，对一个持续后台记录工具不是装饰性问题。

### Findings

- **medium** 本地数据保留策略需要 MVP 默认值（FR-8 / FR-12 / §9 开放问题 4） — PRD 要求本地优先、可删除、可导出，但“本地数据默认保留多久？”仍开放。对个人自用也可以很轻量，但没有默认值会影响数据库增长、删除入口、隐私预期和 SM-1 的长期记录判断。*Fix:* 明确 v1 默认“永久保留直到用户删除”或“保留 N 天可配置”；若暂不做自动清理，也写成非目标。

## Downstream usability — adequate

这份 PRD 对下游还算友好：FR 编号连续，UJ-1/UJ-2 都有命名 protagonist，SM 能回指 FR，术语表覆盖了活跃应用、活动采样、专注片段、分类、本地数据、统计摘要等核心名词。对于个人小工具，这已经足够让 UX、架构和 story creation 做 source extraction。

主要下游风险是少数术语的工程含义不稳定，以及假设索引存在轻微 roundtrip 问题。它们不会推翻 PRD，但值得在进入故事拆分前修掉。

### Findings

- **low** MVP 范围里的 `[ASSUMPTION]` 简写没有完整 roundtrip（§7.1 / §10） — §7.1 中“空闲时间识别 `[ASSUMPTION]`”和“导出本地统计摘要 `[ASSUMPTION]`”没有携带假设文本，§10 索引的是更具体的 FR-3、FR-12 假设。读者能猜到对应关系，但机器抽取和人工复核会多一步。*Fix:* 删除 §7.1 的简写标签，或改成与 §10 完全一致的假设文本。

## Shape fit — strong

PRD 形状匹配产品：这是个人自用、低风险、单操作者、Windows 桌面端小工具，所以它采用 capability spec + 少量 UJ 的形态是对的。没有为单人内部工具塞入过重 personas、市场竞争、企业采购或多角色流程。

同时它也没有轻到只剩愿景：FR、NFR、非目标、MVP 范围、成功指标、反指标和假设索引都在，足以承接后续实现。以这个 stakes 来看，结构密度刚好。
